## 性能分析报告（docs/performance-analysis.md）

全量走读了 miniprogram（381.7 KB / 34 ts）+ 7 个云函数，产出 `docs/performance-analysis.md`。
**只写文档，未改任何代码。**

定位到的关键结论（供后续优化用）：

- **`listRecentProfiles` 单次最多 24 次 DB 查询**（`inventoryApi/recent.js:65-88`）：
  `limit=100` + `MAX_RECENT_ROUNDS=12`，数据不足 100 条时 `cutoff` 逻辑退化成跑满 12 轮 ×2 状态；
  每轮还对累积 rows 全量重排。**小数据量用户反而最亏**。修法：加提前退出 / 建 `ownerId+updatedAt` 索引改单次查询。
- **首页 onShow 固定 5 次 DB 读**（4 次 `count` + 1 次列表），无缓存、无脏标记，
  详情页返回也重来。云开发 `count()` 是扫计数，比列表查询贵。
- **分页用 skip(offset)**（`index.js:183/306/587/614`），offset 硬上限 10000 且成本随页码线性。
  改成 `(expiryDate, createdAt)` 复合游标**不需要新索引**（现有索引已覆盖）。
- **批量操作页 O(N²) 下发**（`batch-operation/index.ts:95-125`）：do/while 拉全量 + 每页全量 setData，
  N=1000 时约 16 倍冗余。最省事的修法是「先累积、最后一次 setData」。
- **`dispatchReminders` 逐条串行**（`index.js:238-253`）：每条 6-8 次 DB + 1 次 openapi，
  50 条/批 × 20 批 ≈ 250s，超 60s 超时 → **超时后剩下的提醒第二天会被判 REMINDER_MISSED 直接取消，用户永远收不到**。
  改 8 路并发即落到 ~32s。**这项优先级应最高**（会丢用户数据语义）。
- 其他：搜索正则三字段 OR 里 `{name: keyword}` 是纯冗余（`searchName` 已是小写 name）；
  写操作事务外 `getOwnedItem` 与事务内读重复；`processBatch` 20 并发事务 / `cleanupTrash` 100 并发；
  `generateCover` 的 `name` 等值查询没有索引；封面 1024² 原图直出且无 `lazy-load`。

报告里明确列了「不建议做的事」：不分包（体积太小）、不上虚拟列表、不去掉 version 并发控制、
不调大 `cloud.ai()` 超时预算。

## 排查「推上去了却一直显示 69 个待推送」

**结论：远端已是最新，69 是假象。**
- `git ls-remote origin` → `refs/heads/index-ui` = `d8c6499` = 本地 HEAD，一条都没差。
- 假象来源：`.git/packed-refs` 里残留一条 **9/9 的老记录** `417b21e refs/remotes/origin/index-ui`，
  而真正的松散引用目录 `.git/refs/remotes/origin/` **不存在**（9/10 那次 `.git/refs` 被清空后只 `mkdir -p` 到 `remotes` 层，没补 `origin`）。
  git 拿 packed-refs 那条老值去比 → 永远 ahead 69。

**关键发现：带斜杠的引用在本环境里建不出来（待龙哥自己终端复核）**
- `git branch probe/nested` → **静默失败**：分支不生成、`refs/heads/probe/` 目录不生成、零报错。
- `git update-ref refs/heads/a/b <sha>`、`refs/remotes/origin/main` 同样静默失败。
- 同环境里 `refs/remotes/zztest2`、`refs/heads/index-ui`（都是**单层文件**）能写成功。
- **两套 git 都复现**：`C:\Program Files\Git` 的 2.53.0.windows.2 + WorkBuddy 自带 PortableGit 2.55.0.windows.3；
  连全新 `git init` 的空仓库也复现 → 大概率是我这边执行环境（沙箱/进程级拦截）所致，**不一定是龙哥本机 git 坏了**。
- 且 `git fetch`/`git update-ref` 一跑，会把我手工补出来的 `refs/remotes/origin/` 目录连带删掉，所以手工补目录只是临时状态。

**已做的处理（只在 `.git` 内，未动工作区）**
- 备份 `.git/packed-refs` → `.git/packed-refs.bak-20260912`。
- 清掉 packed-refs 里那条过期记录（现只剩表头）→ status 从假的 `[ahead 69]` 变成诚实的 `[gone]`，不再谎报待推送。
- 清掉全部诊断临时文件，撤销测试用空提交 `aaf3936`，HEAD 回到 `d8c6499`，`--porcelain` 为空。

**待验证**：龙哥在自己终端跑 `git fetch origin` + `git status`。恢复成干净的
`## index-ui...origin/index-ui` 就说明只是我这边沙箱问题；仍是 `[gone]` 就是本机 git 建不了
`refs/remotes/origin/`，需重装/换版本 Git 或查公司安全软件。

**排查手法（可复用）**：先 `git ls-remote origin` 拿远端权威值，再和 `git rev-parse HEAD` 对比——
只要两者相等，「待推送 N」就是本地引用坏了，跟提交本身无关。
