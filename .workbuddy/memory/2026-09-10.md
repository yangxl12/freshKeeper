## Git 对象丢失的恢复（重要）

- 现象：`git status` 突然报 `fatal: bad object HEAD`，`git fsck` 显示大量 dangling/无效 refs，松散对象只剩 7 个
  （历史提交对象全丢）。怀疑与 `git stash push -- <path>` 失败（报 `d1b17d82... is not a valid object`）同时发生。
- 恢复：`git ls-remote origin` 发现远端 `refs/heads/index-ui` 与本地 HEAD 同点（历史都已推送），
  直接 `git fetch origin` 即把缺失对象拉回，随后 `git log/status/commit/push` 全部正常。

- 教训：本仓库历史一定要及时 push，远端是唯一的兜底备份；不要在仓库里跑失败风险高的 stash。

## 调研：快速录入接入云开发 AI（未改代码）

- 产出 `docs/ai-parse-research.md`。结论：用**云函数端** `@cloudbase/node-sdk` 的 `app.ai()`，不用小程序端 `wx.cloud.extend.AI`。
  理由：云函数端无基础库版本要求（项目 libVersion 3.8.10，小程序端要用 Hy3 得升到 3.15.1，有用户兼容风险）、
  prompt 不暴露在包内、可在服务端做限频/缓存/校验、能直接复用 `cloudfunctions/quickEntryApi/validation.js`。
- 计费：Token 点 1000 点 = 1 元；DeepSeek-V4-Flash 输入 1000 点/百万、输出 2000 点/百万。
  单次解析（400 in + 300 out）≈ 1 点 = 0.001 元，50 元 ≈ 5 万次。成本不是问题。
- 免费路径：「小程序成长计划」（微信公众平台 → 行业能力，2026 年内有效）送 10 亿混元 Token，**仅限小程序和云函数中使用**。
  坑：免费体验版环境控制台里「CloudBase 内置模型调用」显示不支持，个人版（19.9/月）才支持 —— 需先确认
  `cloud1-d0gkh66ce94b1be08` 的套餐等级，或报名成长计划把它升级为个人版。自定义大模型要标准版 199/月，本项目不需要。
- 无 `response_format: json_schema` 严格模式。先用 prompt 强约束 + few-shot，服务端 `JSON.parse` 失败重试一次再降级；
  不够稳再上 `streamText({ tools })`（function call 按 schema 出参）。
- 设计要点：prompt 必须要求「未提及的字段返回 null，禁止推测」，靠现有 `dateCandidates.role='unknown'`
  → `confirmationFields` 机制兜幻觉，而不是让模型编数量。
- 接入点：`miniprogram/services/quick-entry-service.ts:56`（现调 `parseQuickTextLocally`）＋ `config/runtime.ts` 的 `QUICK_ENTRY_FEATURES`；
  云函数返回结构保持 `QuickEntryParseResult` 不变，下游 `createDraftFromParsed` 零改动。
- 语音：语音转文字不属于大模型能力，「按住说」要另接**微信同声传译插件**（`wx.getRecordRecognitionManager`），转文字后再走同一套抽取。

## 制定：快速录入接入 AI 解析的完整实现计划（未改代码）

- 产出 `docs/ai-parse-plan.md`。用户已拿到云开发免费 token，要求"准确识别 + 准确获取有效信息"。
- **纠正了旧调研的三处错误**（用户给的链接 https://docs.cloudbase.net/ai/ai-inspire-plan-guide + wx-server-sdk 文档）：
  ① 云函数端应用 `wx-server-sdk` 的 `cloud.ai()`（本项目已装 4.0.2，要求 ≥3.0.5-beta.1），不是 `@cloudbase/node-sdk` 的 `app.ai()`；
  ② 模型用 `hy3`，`hy3-preview` 官方已公告即将下线；
  ③ provider 用 `cloudbase`（免费额度优先，耗尽自动转套餐额度），`hunyuan-v3` 只吃免费额度、来源不允许直接报错。
  返回取 `result.text`；`cloud.init({ timeout: 60000 })`；控制台需**手动开启 hy3 模型开关**。
- 计划核心是"准确"这个目标的技术拆解（LLM 做不到 100%，做的是"不确定就交给人确认"）：
  L1 prompt 强约束（未提及必须 null）；L2 **不让模型算日期**——模型只出 `dateFacts`
  （absolute 给年月日 / relative 给 offsetDays / shelf_life 给 value+unit），换算全交给现成 `date-facts.js:normalizeFacts()`；
  L3 **证据回链**——模型每个非推断字段必须给 `evidence` 原文片段，服务端去空白后校验它确实出现在用户原文里，
  对不上就置 null 走 `confirmationFields`。这一招专治"买了牛奶 → 模型硬编 quantity:1"。
- **关键踩坑预警**：`normalizeTextResult()` 用 `assert` 抛错，一条 item 里一个脏字段会让**整批**请求抛
  `INVALID_PROVIDER_RESPONSE`，前端直接降级、连识别对的物品一起丢。所以 ai-parse 层必须先做**逐字段宽容清洗**，
  再喂给它做严格兜底校验；两层职责不同（宽容 sanitize vs 严格 validate）。
- 文件清单：新增 `cloudfunctions/quickEntryApi/{ai-client,ai-prompt,ai-parse,ai-quota}.js` + `tests/unit/ai-parse.test.ts`；
  改 `index.js`（parseText 加 AI 分支 / getCapabilities 加 aiText）、`config.json`、
  `miniprogram/config/runtime.ts`（加 `aiParse`）、`pages/quick-entry/index.ts`（loading 文案 + `AI` 徽章）。
  **不动** `services/quick-entry-service.ts` 与 `domain/quick-entry.ts`——返回结构保持 `QuickEntryParseResult` 不变。
- 验收用例 6 条（含"买了三个苹果"unit 必须 null、"牛奶"单独输入 quantity 绝不许填 1、"今天天气怎么样"不产物品），
  目标字段级 precision ≥ 0.95、recall 允许偏低（宁可说不知道，不许猜错）。分 P0/P1/P2 三阶段。

## 纠偏：AI provider 必须用 hunyuan-v3，不是 cloudbase（用户报的坑）

- 用户去控制台"开 hy3 模型"，被提示"不是资源点计费，需先切换为资源点套餐"。查明：**那个开关属 `cloudbase` provider 专有**，
  且 `cloudbase` **仅资源点套餐可用**。本项目环境是非资源点计费（成长计划一期报名的环境是"配额制套餐"，体验版同理），所以被拦。
- **正解：不要切套餐，不要开开关**。改用 `ai.createModel("hunyuan-v3")` + `model: "hy3"` —— 微信官方 FAQ 的原话。
  `hunyuan-v3` 的适用套餐是"资源点、非资源点均可"，**无需开启也不支持关闭**，且**仅消耗免费额度**。
- 代价（都已写进计划的降级设计）：

  ② 体验模型**单环境仅 5 并发**，超了报 `EXCEED_CONCURRENT_REQUEST_LIMIT`，必须退避重试。
- 将来额度真耗尽再切资源点套餐，届时只改 `ai-client.js` 里的一行（`hunyuan-v3` → `cloudbase`）。

## 实现：AI 解析 P0 打通链路（commit 4c0f835，已 push）

- 新增 `cloudfunctions/quickEntryApi/ai-client.js`：**唯一**知道 `cloud.ai()`/provider/模型名/返回结构的地方。
  `aiEnabled()` 读 `QUICK_ENTRY_AI_ENABLED`；provider `hunyuan-v3`、model `hy3` 均为常量 + 环境变量覆盖；
  `createTextGenerator({ sdk })` 可注入假 SDK（单测用，**顶层不 require wx-server-sdk**，只有调用时才 lazy require，
  否则单测会去加载真 SDK）。返回结构收敛在 `extractText()`：`result.text` → `result.messages[].content` 逐级退化。
- 已核实 SDK 4.0.2 内部：`cloud.ai()` → `@cloudbase/node-sdk` 的 `tcbInstance.ai()` → `@cloudbase/ai`。
  `createModel('hunyuan-v3')` **不在 MODELS 表**（表里只有 hunyuan/hunyuan-beta/ark/dashscope/01-ai/moonshot/zhipu/hunyuan-exp/hunyuan-open/deepseek），
  因此走 `DefaultSimpleModel` 分支，URL = `…/v1/ai/hunyuan-v3/chat/completions`，body 原样透出 `{ model:'hy3', messages, stream:false }` —— 正是官方 FAQ 的路子，不用自己拼 URL。
  `generateText()` 返回 `{ text, messages, usage, rawResponses }`，取 `result.text` 确认无误。
- `ai-prompt.js`：system prompt + **4 条 few-shot**（完整句 / 相对时间 / 只有名称 / 保质期）。
  铁律写死：未提及一律 null、禁止算日期（今天=0/明天=1/2周后=14）、没写数量绝不许填 1、category 白名单。
  用户输入用 `"""` 围栏包住并把连续引号替换成全角防越狱；`buildRepairMessages()` 用于 JSON 解析失败后的纠正重试。
- `ai-parse.js`：`aiParseText({ text, serverToday, generate, timeoutMs })`。
  链路 = 调模型 → `extractJson()`（容错 ```json 围栏 + 前后解释文字，截首个 `{` 到末个 `}`）→ 失败**重试一次** →

  `normalizeTextResult()` 严格兜底 + 日期换算。`parserVersion = 'ai-v1'`（P2 的 `AI` 徽章按 `ai-` 前缀判断）。
- **超时预算用独立的 `QUICK_ENTRY_AI_TIMEOUT_MS`（默认 6000）**，取 `min(它, QUICK_ENTRY_TIMEOUT_MS)`。

- `index.js`：`parseText()` 里 AI 是**纯加速路径**，catch 一切错误静默降级 provider/本地 rules-v3，

## 部署：quickEntryApi 上线 + 云端真调验证 AI（commit e4cf321，已 push）

### 结论先说

- **额度已到账**，`hunyuan-v3` + `hy3` 直连可用，线上 `parserVersion = 'ai-v1'`，`getCapabilities().aiText = true`。
  拿到的真实用量：`{prompt_tokens: 748, completion_tokens: 60}`。
- **不需要点任何控制台开关**。控制台那个 `hy3` 开关属 `cloudbase` 通道，与本方案无关，别去动。
- **唯一要手动做的一件事：把 `quickEntryApi` 的超时从 3 秒改成 60 秒**（原因见下）。

### 最大的坑：`config.json` 只在函数首次创建时生效

- `cloudfunctions/quickEntryApi/config.json` 里的 `timeout` / `envVariables` **不随"更新部署"应用**。
  `cli cloud functions deploy`（以及开发者工具对**已存在**函数的上传）**只更新代码**，不重新写函数配置。
  只有 `CreateFunction` 走通（= 函数不存在/被删）时，`updateFunctionConfig` 才会被调用把
  `timeout` / `envVariables` / `triggers` 写上去。IDE 里 `updateFunctionConfig` 的字段映射就在
  `app.asar` 的 `async updateFunctionConfig(e){...}`，`envVariables` → `Environment.Variables` 是支持的，问题纯在调用时机。
- 三层证据：① `cli cloud functions info --env ... --names quickEntryApi --project ...` 显示 `timeout: 3`、
  `runtime: Nodejs16.13`（config.json 写的是 60）；② 新代码已上线（响应里有 `aiText` 字段）但 `aiText=false`
  → 说明不是代码没更新，是环境变量没到；③ 五条物品的长输入报
  `errCode: -504003 FUNCTIONS_TIME_LIMIT_EXCEEDED ... timed out after 3 seconds`。
- 修法：云开发控制台 → 云函数 → quickEntryApi → 配置 → 超时时间改 60 秒（推荐）；
  或删函数重新部署（会重置调用权限，慎用）。**CLI 没有改函数配置的命令**，IDE 的 HTTP 服务端也只有
  `/cloud/functions/{list,info,deploy,inc-deploy,download}` 这几条路由，没有配置更新入口。

### 因此改的设计：开关默认开启

- `ai-client.js` 的 `aiEnabled()` 从「默认关闭」改成「**默认开启 + 急停开关**」：
  `QUICK_ENTRY_AI_ENABLED` 取 `false`/`0`/`off`/`no` 才关闭（否则开启）。
  理由：开启若依赖环境变量，新环境部署完就是死的（环境变量只能在控制台设）。
  额度耗尽时在控制台把它设成 `false` 即可整体停用整条 AI 链路，不用重新部署。
- 代价与收益：这是"部署即可用"的取舍。计划原文没规定默认值，已同步写进 `docs/ai-parse-plan.md` 第 12 节。

### 实测延迟（决定超时必须调大的直接依据）

| 输入 | 耗时 |
| --- | --- |
| 单条 `牛奶2盒9月12日过期放冰箱` | 1.9~2.4s |
| 单条（相对时间 / 保质期 / 无数量） | 1.6~2.1s |
| 五条物品的长输入 | **~4.9s → 撞 3s 超时，直接失败** |

15 秒内并发 4 次调用时 `getCapabilities` 只用了 524ms，说明冷启动开销不大，瓶颈是模型本身。
**在 3s 超时下，单条勉强能过、多条必挂**，所以超时那一步不是可选项。

## 本地调试 404 诊断（commit 4abc198，已 push）

用户贴出云函数本地调试日志，关键行：`{"resultCode":"AI_PARSE_DEGRADED","reason":"404","durationMs":485}`。

- **根因**：微信开发者工具的「云函数本地调试」跑本地 node 进程，**没有云开发网关注入**，
  `cloud.ai()` 的 `/v1/ai/` 请求直接 404（485ms 快速返回，不是超时）。功能没坏——随后静默降级本地规则，
  接口正常返回 `resultCode:"OK"`。**AI 路径只能在云端验证**（关本地调试，用模拟器/真机）。
- 证据链：`@cloudbase/app/src/libs/adapter-node/request.ts:157` 的 `UNSUPPORTED_V3_SIGN_PATH` 含 `/v1/ai/`，
  该路径要 `getClientCredential()` 换 Bearer Token，本地调试没有这套注入；
  `adapter-node/wx.ts:26` 用 `TENCENTCLOUD_RUNENV === 'WX_LOCAL_SCF'` 区分本地/线上形态——**直接复用这个变量**。
- **已修**：`ai-client.js` 新增 `isLocalDebug()`，`aiEnabled()` 在本地调试下返回 false（`capabilities.aiText` 随之 false）；
  逃生门 `QUICK_ENTRY_AI_LOCAL_DEBUG=true` 可强制开启；`QUICK_ENTRY_AI_ENABLED=false` 优先级仍最高。
  测试在 `ai-parse.test.ts` 的 `ai client adapter` 段。`npm run check` 176 测试全绿。

## 两条待办的含义（已被用户问过，解释一次）

- **隐私指引**：用户输入文字 → 云函数 → 混元，属于「提供给第三方处理」，必须在小程序后台
  设置 → 服务内容声明 → 用户隐私保护指引 里声明；不过审就把 `QUICK_ENTRY_FEATURES.aiParse` 置 false。
- **真机日志复核**：`AI_CONCURRENCY_RETRY`（撞 5 并发，已退避重试）/ `AI_PARSE_CACHE_HIT`（缓存命中省额度）/
  `AI_QUOTA_NEAR_LIMIT`（某 openid 到 40 次）/ `AI_TOKEN_USAGE`（token 消耗）。日志全在云函数端，
  本地跑单测看不到，必须真机调用才会打出来。日限 50 的判断标准是**会不会误伤自己**，不是钱
  （单次约 0.001 元）；要调只改环境变量 `QUICK_ENTRY_AI_DAILY_LIMIT`，不用重新部署。
  另两条顺手看：`AI_QUOTA_EXCEEDED`、`AI_EVIDENCE_REJECTED`（后者反映模型质量）。

## AI 生成物品封面小图（commit c2bd1b9，已 push，inventoryApi 已部署）

- 需求：物品添加时用 AI 按名称生成手绘风小图替换首页卡片默认占位图，失败兜底默认图。
- **生图通道（已核实 SDK 4.0.2 源码）**：`cloud.ai().createImageModel('hunyuan-image')` →
  `generateImage({ model:'hunyuan-image', prompt, n:1 })`，POST `…/v1/ai/hunyuan-image/images/generations`，
  返回 OpenAI 风格 `{ data:[{ url }] }`（临时 URL 会过期，**必须下载转存云存储**，物品只落 fileID）。
  provider/模型名只出现在 `cloudfunctions/inventoryApi/image-cover.js`。
- 云函数侧：`inventoryApi` 新增 `generateCover` action（`image-cover.js` + index.js）。
  逻辑：已有 `coverFileId` 直接返回 → 同名 active 物品复用封面 → 否则生图 → https 下载 → `cloud.uploadFile`
  到 `covers/<sha1(ownerId)前16>/<itemId>-<ts>.png` → update 物品。
  **封面是展示数据，故意不 bump version**（避免与并发编辑打出 CONFLICT）。
- 超时预算：函数整体 10s，生图 8s + 下载 6s 各自 `Promise.race` 独立限制；急停开关 `COVER_IMAGE_ENABLED`
  （默认开，false/0/off/no 关，与 QUICK_ENTRY_AI_ENABLED 同约定）。
- 前端：`generateItemCover()`（inventory-service）+ 两个 fire-and-forget 触发点：
  ① quick-entry `persistDrafts` 成功后 `requestCovers(savedItemIds)` **串行**（避开生图并发限制）；
  ② item-form-sheet 新增（非编辑、非恢复）后单条生成。失败全静默。
- `inventory-row`：wxml `src="{{coverSrc}}"` + `binderror="handleCoverError"`；data 记 `coverFor/coverError`，
  observer 只在封面 ID 变化时重置错误态重新加载，同一封面失败后不反复重试。
  `<image src="cloud://fileID">` 小程序原生支持，无需换临时链接。
- 单测 `tests/unit/image-cover.test.ts` 12 条（假 SDK 注入；顶层不 require wx-server-sdk）。
- **待真机验证**：线上实际生图延迟与成图质量；若 10s 不够需在**控制台**改 inventoryApi 超时
  （config.json 只在首次创建时生效）。未做的事：编辑改名不重新生成；item-detail 页仍用默认图。

## 封面功能「看起来没实现」的根因排查与修复（同日晚）

上线后首页列表从来没出现过封面。用模拟器探针（`wx-probe/probe-cover.js`：save 造物品 → generateCover → get 回读）
实测抓到真实报错，三个根因叠加：

1. **线上 inventoryApi 超时是 3 秒**（致命）。实测 `errCode: -504003 Invoking task timed out after 3 seconds`，
   而 cloud.init 默认 SDK HTTP 超时约 15s、生图 4.7s+。`config.json` 写 10 也没用——
   **已存在函数的 config.json 不再生效，部署也改不了，CLI 没有改配置的命令**，只能控制台改。
   已在 `index.js` 加 `cloud.init({ env, timeout: 45000 })`（覆盖 SDK 内部 ~15s 默认值，这个写代码里是生效的）。
2. **model 名 `hunyuan-image` 已于 2026-07-15 下线**（致命）。provider 仍叫 `hunyuan-image`，
   但 `generateImage({model})` 必须传具体版本：`HY-Image-3.0-Plus-4090-Tob-v1.0`。
   同时**必须显式关 `revise:{value:false}`（+10s）和 `enable_thinking:{value:false}`（最长 +60s）**，
   否则必撞超时。预算改成生图 30s / 下载 10s。
3. **前端不回填**（体验）。封面是异步落库的，首页 `onShow` 拉列表早于生图完成，卡片停在占位图且不自愈。
   已加进程内通知：`inventory-service.ts` 的 `onItemCoverReady(listener)`，
   `generateItemCover` 成功后广播 `{itemId, coverFileId}`；首页 onShow 订阅 / onHide 退订，
   收到直接 `patchItem` 补到卡片。零额外请求、无轮询。

- 验证探针踩坑：云函数返回是 `{ok:true, data:{...}, requestId}`，**取字段要 `result.data.itemId`**，
  直接 `result.itemId` 会静默拿到 undefined；`idempotencyKey` 必须是标准 UUID v4，否则 `INVALID_ARGUMENT`。
- 单测同步：`GENERATE_TIMEOUT_MS + DOWNLOAD_TIMEOUT_MS < 50_000`（对齐 60s 云函数超时），
  新增"model 必须是带版本号的实名、revise/thinking 必须关"的防回归断言；`inventory-service.test.ts` 加 2 条广播测试。
- **上线上限**：60s 超时只能用户在云开发控制台手动改（本机 CLI 无此能力）。
