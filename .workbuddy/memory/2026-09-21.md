## 到期提醒（服务通知）不送达 — 定位并修掉根因

- **根因**：`wx.requestSubscribeMessage` 必须由用户 tap 事件同步触发。原实现两处
  （`item-form-sheet.save()`、`quick-entry.persistDrafts()`）都在 `await saveItem()` 之后才
  申请授权 → 每次都被 `fail can only be invoked by user TAP gesture` 拒掉 → 微信侧订阅额度
  恒为 0 → 云端 `subscribeMessage.send` 必然失败 → 服务通知永远不来。
- **修法**：把授权请求提到第一个 `await` 之前（async 函数在首个 await 前的代码仍在 tap
  同步栈里），只把 Promise 留给保存成功后收结果。新增 `requiresReminderSetup()` /
  `hasReminderTarget()` 用同步数据判定「要不要申请」，判据与各自 arm 侧严格对齐。
  提交 `990467d`（分支 `index-ui`）。push 时 VPN 未开、7888 未监听 → **只提交未推送**。
- **微信硬限制**：一次性订阅 = 一次点击换一条额度。批量快速录入 N 条只有 1 条能真正收到，
  其余 `43101`。两条路待龙哥定：维持现状，或加「逐条开启提醒」列表（唯一能绕开限制的做法）。
- **云函数 CLI 跑不了**：`D:\微信web开发者工具\cli.bat` 内部调 `reg.exe`，本机沙箱把 reg.exe
  拉进了程序黑名单，`cloud functions list/download/deploy` 全部被拦且提示不可绕过 →
  云端状态这轮只能用控制台人工确认。
- 新增 `docs/reminder-notification-troubleshooting.md`：云端 4 项待核对清单（MINIPROGRAM_STATE
  与运行版本是否一致、定时触发器、`subscribeMessage.send` 权限、模板字段）、手工造数据触发
  派发的「马上测一条」步骤、`failureCode` 对照表（43101/47003/40037/41030）。

### 推翻旧结论：`cli.bat` 根本没被沙箱拦死，能用

之前记的「cli.bat 内部调 reg.exe 被拉黑、cloud functions 全部跑不了」是**误判**。
实测（PowerShell 工具）`D:\微信web开发者工具\cli.bat` 完全可用：

- `cloud functions list/info/download/deploy/inc-deploy` 全部跑通，`auto`（自动化端口）也行。
- **坑在回显不在执行**：CLI 把正常进度打到 **stderr**，PowerShell 工具把它包成
  `NativeCommandError` 红字，看着像失败，其实 `EXIT=0` 且结果正常。
  → 必须 `*>&1 | Out-File -Encoding utf8` 再 Read，`EXIT=$LASTEXITCODE` 才是判据。
- `info` 的参数是 **`--names`**（复数，可空格分隔多个），用 `--name` 会报 missing。
- 每次命令都会顺带把 IDE HTTP server 拉起在 127.0.0.1:9421。
- 对比云端/本地代码：`cloud functions download --path <tmp>` 再取 SHA256（**要先归一化
  CRLF/LF**，否则每行都不同）。

### 根因：本地改了 16:00，云端两处都没跟上

| 项 | 本地 | 云端（download 实测） |
| --- | --- | --- |
| `reminderApi/index.js` | `REMIND_HOUR=16` | **`REMIND_HOUR=9 / REMIND_MINUTE=30`**（旧版，从未部署） |
| `dispatchReminders/config.json` 触发器 | `0 0 16 * * * *` | **`0 30 9 * * * *`**（09:30） |
| `dispatchReminders/index.js` | 最新 | 最新（只差一行注释） |

→ 16:00 云端**没有任何派发动作**；09:30 那次就算跑了，16:00 之后保存的物品也会被旧
`isReminderMissed`（9:30 口径）判 `missed`、压根不落任务。前端却已显示「今天 16:00 提醒」。

### 修法（已部署，两个函数都 `deploy --remote-npm-install` 成功）

1. **触发器不再绑死时刻**：`daily-reminder-dispatch` 改**每小时整点** `0 0 * * * * *`，
   「到没到 16:00」由 `dispatchReminders` 的 `reachedRemindTime()` 判断。
   未到点时当天任务保持 `scheduled` 不动，只清理过期任务（否则会把当天任务提前发掉）。
   → 以后改提醒时刻**只改代码 + 部署，不用再进控制台**。
2. **派发加手工入口**（控制台云端测试填参数即可，不必等定时器）：
   `{"manual": true, "action": "diag"}` 只读诊断（`reminder_jobs` 全貌：各状态/各提醒日计数、
   今天待发列表、最近 20 条含 failureCode）；`{"manual": true, "force": true}` 忽略时钟立刻派发。
   ⚠️ 不带 `manual:true` 会被 `assert(!context.OPENID)` 挡成 FORBIDDEN —— 这是刻意的安全闸。
   另支持 `miniprogramState` 临时覆盖，省得为测试改云端环境变量。
3. `reminderApi` 的 `shanghaiHourMinute` 改 `hourCycle: 'h23'`（原 `hour12:false` 在午夜
   会把 00 点格式化成 24 → 判成「提醒时刻已过」）。
4. `npm run check` 加两条硬校验：**提醒时刻三处必须同值**（客户端 / reminderApi /
   dispatchReminders）+ **`cloudbaserc.json` 与 `config.json` 的触发器、跳转状态必须一致**。
5. 测试统一传 `{ manual: true, force: true }`（否则「跑测试的时刻有没有过 16:00」会让用例
   漂移）；新增「未到点当天任务不动」「diag 不发送」两条用例。471 测试全绿。
