## 1. 结论摘要

当前架构适合作为微信云开发 MVP：小程序侧已经形成 `page/component → domain/service → cloud function` 的基本分层，云端以可信 `OPENID` 隔离用户，核心写操作具备字段白名单、版本冲突控制和快速录入幂等键，日期统一按上海自然日处理，测试数量也明显高于同体量项目的常见水平。

但仓库当前状态还不能直接判定为“可发布”。本轮发现：

- 1 个 P0 发布阻断项：提醒模板仍是占位配置，且代码与部署文档的配置方式、模板字段和触发时间互相矛盾。
- 6 个 P1 高优先级问题：概览缓存失效链路缺失、数据导出使用旧提醒字段、库存游标可能漏记录、封面文件生命周期不闭环、AI 能力缺少可靠成本保护、提醒派发异常会留下不可恢复任务。
- 8 个 P2 中优先级问题：概览卡与筛选条件不一致、反馈未真正提交、字段长度缺少服务端上限、批量页无加载上限、最近档案可能被过早截断、回收站仍用偏移分页、数量调整走重写路径、云函数依赖存在上游审计告警。

建议先修数据正确性和发布配置，再处理成本、任务恢复与分页；不要先做框架迁移或大规模重构。

## 3. 架构评估

### 3.1 当前结构

```text
小程序页面 / 组件
  ├─ domain：日期、库存展示、快录草稿规则
  ├─ services：统一云函数调用与客户端能力封装
  └─ utils：埋点、跨页意图、本地时间与迁移辅助
          ↓
云函数 API
  ├─ inventoryApi：库存查询、写入、批量、回收站、封面
  ├─ userApi：资料、设置、导出、注销
  ├─ quickEntryApi：文字/语音/OCR/AI 解析
  ├─ reminderApi：提醒预约
  ├─ dispatchReminders：定时派发
  └─ cleanupTrash：定时清理
          ↓
云数据库 / 云存储 / 微信 OpenAPI / 云开发 AI
```

### 3.2 做得较好的部分

1. **边界清楚且技术栈克制。** 原生小程序没有额外引入状态库和 UI 框架，符合当前规模；服务调用集中在 `miniprogram/services`，业务展示规则主要在 `domain`。
2. **服务端身份可信。** 各 API 从 `cloud.getWXContext().OPENID` 取用户身份，并拒绝客户端提交 `ownerId/openid/templateId` 等字段。
3. **写入一致性基础较好。** 库存状态操作使用 `version` 条件更新，快速录入使用稳定 ID 与指纹实现幂等，批量写使用受控并发。
4. **日期口径明确。** 到期状态、提醒日期和跨日刷新都围绕 `YYYY-MM-DD` 与 `Asia/Shanghai` 设计，避免了大部分设备时区偏差。
5. **降级思路成熟。** 快速录入具备 AI → 自定义服务 → 本地规则的降级，封面生成失败不阻断物品保存。
6. **已有性能治理痕迹。** 首页合并列表与概览请求、库存采用键集游标、列表设置 200 项上限、定时任务和批量写限制并发，方向合理。

### 3.3 主要架构债务

- 页面状态机过大：`quick-entry/index.ts` 1,031 行、`home/index.ts` 599 行、`mine/index.ts` 568 行；`inventoryApi/index.js` 672 行并承担查询、统计、写入、历史、封面和路由。现在仍可维护，但变更容易跨功能产生回归。
- 跨模块契约靠人工同步：提醒模板、提醒字段、上海时间、导出字段分别散落在多个云函数和文档中，本轮已经出现实际漂移。
- 缓存失效属于页面私有实现，而写入口分布在服务、详情、表单、快录、批量和回收站，导致“谁修改、谁记得失效”的脆弱结构。
- 云函数主体仍是无类型 JS，根 `tsconfig.json` 不覆盖它们；大量云数据库结果和 OpenAPI 响应只靠运行时约定。
- 存在死接口/死状态迹象：`decrementItem` 没有调用方，`pendingInventoryIntent` 已无消费方，`validateOptionalStorage` 只导入未使用。它们本身不致错，但会干扰后续判断真实架构。

建议采用小步重构：优先抽取共享“库存变更/缓存失效”模块和提醒契约，不建议为了拆文件而一次性重写页面或迁移框架。

## 4. 问题清单

### P0-01 提醒功能在仓库基线中不可用，发布配置契约互相矛盾

**证据**

- 客户端模板 ID 仍为占位值：`miniprogram/config/runtime.ts:15`。
- `reminderApi` 同样硬编码占位值，并在 `arm` 时明确拒绝：`cloudfunctions/reminderApi/index.js:18, 141-145`。
- 派发模板字段仍是示例序号：`cloudfunctions/dispatchReminders/template.js:13-18`。
- 实际触发器是 09:30：`cloudfunctions/dispatchReminders/config.json`；但 `docs/launch-checklist.md:96` 和 `docs/cloud-deployment.md:221-242` 多处仍写 09:00。
- `reminderApi` 注释明确说明模板 ID 不读环境变量，但 `docs/launch-checklist.md:14-17` 和 `docs/cloud-deployment.md:206-220` 又要求配置环境变量。
- 当前 `dispatchReminders` 的 `MINIPROGRAM_STATE` 为 `developer`，正式版发布前必须改为 `formal`。

**影响**

按当前代码直接部署，用户即使同意订阅也无法成功预约；若运维只照旧文档设置环境变量，代码仍会继续使用占位值。模板字段类型或触发时间配错时，还会出现“授权成功但不发送/发送失败”的隐蔽故障。

**建议**

1. 以 `reminder-redesign-plan.md` 的 09:30 和“代码内固定模板契约”为唯一口径，或统一改成可靠的环境配置，二选一，不保留双轨说明。
2. 确认真实模板字段后同时更新客户端 ID、`reminderApi` ID 与 `template.js` 字段映射。
3. 在发布检查脚本中增加：禁止 `TODO_`、校验前端时间与 cron 一致、校验 `MINIPROGRAM_STATE`、输出需要人工确认的模板字段。
4. 在体验版真机完成“授权 → 定时派发 → 消息点击详情”闭环后再发布。

### P1-01 首页概览缓存不会被页面外写操作失效

**证据**

- 缓存和 `overviewDirty` 定义在首页模块：`miniprogram/pages/home/index.ts:42-93`。
- 全仓只有首页自己的操作会调用 `markOverviewDirty`：`miniprogram/pages/home/index.ts:173-175, 217, 234, 479, 531, 553`。
- 新增、编辑、重新入库在 `item-form-sheet/index.ts:401-431` 完成；详情页的用完/删除/彻底删除在 `item-detail/index.ts:97-147` 完成；这些路径都没有失效概览。
- 首页 `onShow` 虽会刷新列表，但只有缓存不可用时才向 `listInventory` 请求概览：`miniprogram/pages/home/index.ts:305-342`。

**复现**

1. 打开首页并成功加载概览，使缓存变为 clean。
2. 进入快速录入新增一件物品，或在详情中把物品标记为已用完。
3. 返回首页：列表会刷新，但顶部“在库/临期/已过期/已用完”仍可能保持旧数字。

注销也有同类问题：`wx.clearStorageSync()` 只清持久化缓存，不会清模块内的 `overviewCache`；同一 JS 进程内 `reLaunch` 后仍可能显示注销前数字。

**建议**

把概览缓存和失效方法移到一个很小的共享模块，并在 `inventory-service` 的所有成功 mutation 中统一失效；注销时显式清内存和持久化缓存。补充“新增/编辑/用完/删除/恢复/批量/注销后概览更新”的页面级测试。

### P1-02 数据导出仍使用旧提醒字段，导出结果会丢失提醒日期与关联物品

**证据**

- 导出读取 `remindAt`、`createdAt`、`inventoryItemId`：`cloudfunctions/userApi/export.js:19-26`。
- 当前提醒任务实际写入的是 `itemId`、`remindDate`、`acceptedAt`：`cloudfunctions/reminderApi/index.js:159-170`。
- 导出测试夹具仍构造旧字段 `remindAt`：`tests/unit/user-profile-cloud.test.ts:243, 280-285`，因此测试绿色但没有覆盖真实生产结构。

**影响**

用户导出的 `reminders` 中关键字段会变成 `null`，数据可携带性承诺不完整；后续若用导出文件做恢复或客服排查，也无法关联物品。

**建议**

按当前任务结构导出 `itemId/remindDate/acceptedAt/sendAttemptedAt/sentAt/status/failureCode` 等用户可理解字段，移除内部 `templateId/ownerId`。用 `reminderApi.arm` 的真实结构做契约测试，并评估把导出 schema 版本从 1 升到 2。

### P1-03 库存键集游标缺少唯一排序键，时间相同的记录会被漏掉

**证据**

- 游标只保存 `expiryDate + createdAt`：`cloudfunctions/inventoryApi/index.js:142-160`。
- 查询排序只有 `createdAt`，或 `expiryDate + createdAt`：`cloudfunctions/inventoryApi/index.js:325-355`。
- 下一页使用严格 `<`/`>`，没有 `_id` 兜底：`cloudfunctions/inventoryApi/index.js:328-345`。
- 快速录入最多 20 条并发保存：`miniprogram/pages/quick-entry/index.ts:945-956`，这些记录的服务端时间可能相同。

**影响**

若一页边界两侧有相同 `createdAt`（默认排序还要求 `expiryDate` 相同），下一页条件会排除所有等值记录，首页和批量页可能静默缺项。排序结果也不是完全确定的。

**建议**

将 `_id` 作为最后一级唯一排序键并写入游标；所有方向都构造三段式比较条件。同步补齐复合索引和“30 条以上同到期日、同时间戳”的分页测试。

### P1-04 彻底删除和定时清理不会删除 AI 封面，云存储生命周期不闭环

**证据**

- 生图每次上传到新的 `covers/.../<item>-<timestamp>` 路径：`cloudfunctions/inventoryApi/image-cover.js:138-141, 189-193`。
- `removePermanently` 只删数据库物品和提醒：`cloudfunctions/inventoryApi/writes.js:121-132`。
- `cleanupTrash` 也只在事务内删除物品和提醒：`cloudfunctions/cleanupTrash/index.js:64-80`。
- 账号注销只能收集数据库中仍存在物品的 `coverFileId`：`cloudfunctions/userApi/account.js:268-287, 318-335`；已彻底删除物品的文件已无法追溯。
- 同名物品会复用同一个 `coverFileId`：`cloudfunctions/inventoryApi/index.js:609-619`，所以也不能在删单条时不加判断地直接删共享文件。

**影响**

云存储费用会随历史删除持续增长；注销说明中的“云端封面图全部删除”对先前已彻底删除的物品并不成立，形成隐私与数据生命周期缺口。并发重复生成同一物品封面还可能产生未被引用的上传文件。

**建议**

采用一种明确且可验证的生命周期方案：给 `covers/` 配置保守生命周期并保证活跃封面可重建；或删除前查询引用数、仅在无其他引用时删文件；或引入轻量资源引用记录。当前存在共享 fileID，实施前必须先处理引用关系。为永久删除、自动清理、并发生图和账号注销补集成测试。

### P1-05 AI 解析额度只存在单实例内存，AI 封面没有用户额度且默认 fail-open

**证据**

- `ai-quota.js` 明确使用进程内 `Map`：`cloudfunctions/quickEntryApi/ai-quota.js:3-18`；冷启动或水平扩容会产生新的独立计数。
- 每日 50 次只是当前实例上的计数：`cloudfunctions/quickEntryApi/ai-quota.js:54-79`。
- 封面能力在环境变量缺失时默认开启：`cloudfunctions/inventoryApi/image-cover.js:39-42`。
- `generateCover` 只有登录、物品归属和开关检查，没有日限额或库存总量限制：`cloudfunctions/inventoryApi/index.js:603-626`。

**影响**

“每日限 50 次”不是可靠的成本上限，脚本请求、冷启动和多实例可绕过；封面生成成本更没有按用户保护。公开发布后可能耗尽免费额度或产生非预期费用。

**建议**

把额度计数放到支持原子更新的持久层或云网关限流，至少覆盖 AI 解析与生图两类昂贵动作；封面开关改为只有显式 `true` 才开启；增加每用户每日额度、总物品上限和全局熔断水位。隐私指引还应明确“物品名称会发送给图像模型生成封面”，当前清单只描述了解析模型。

### P1-06 提醒派发的意外异常不会落任务状态，可能卡死或反复占据批次

**证据**

- 单任务异常在批处理外层被吞掉后只返回字符串 `failed`：`cloudfunctions/dispatchReminders/index.js:255-267`。
- 此分支没有记录 job ID、异常阶段，也没有把任务更新为 `failed/unknown`。
- 异常若发生在 claim 前，任务保持 `scheduled`，下一轮查询还会取到它；若发生在 claim 后，任务保持 `sending`，后续永远不会再被扫描。

**影响**

持续失败的首批任务可能在同一次定时函数内被重复扫描，挤占后续任务；`sending` 僵尸任务则不会自动恢复。汇总日志显示失败数量，但无法定位或修复具体任务。

**建议**

让 `processJob` 返回带阶段的结果；外层 catch 记录去标识化 job 摘要，并尽力把 `scheduled` 更新为 `failed`、把已 claim 的任务更新为 `unknown`。增加“超过阈值的 sending 任务”定时对账/告警，测试数据库读写和 OpenAPI 每个阶段的故障注入。

### P2-01 点击概览卡后仍保留搜索和种类，数字与列表口径不一致

**证据**

概览是全局统计，但 `selectOverviewCard` 只设置 `viewStatus`：`miniprogram/pages/home/index.ts:418-423`。搜索词和种类仍参与下一次服务端查询。

**影响**

例如页面仍保留“牛奶 + 食品”，顶部显示“已过期 5 件”，点击后可能只显示 0～1 件，与“查看已过期物品”的无障碍文案不一致。

**建议**

点击概览卡时清空 `search/category`，保留排序即可；增加组合筛选下点击四张卡的测试。

### P2-02 “意见反馈”只保存在本机，却向用户提示“已收到”

**证据**

`miniprogram/pages/mine/index.ts:451-465` 只把内容写入 `mine_feedback` 本地存储，最多保留 20 条，没有云函数或外部反馈通道，随后提示“已收到，感谢反馈”。

**影响**

开发者永远收不到反馈，用户得到误导性确认；换机、清缓存或注销后内容消失。

**建议**

发布前要么接入真实反馈通道并给出失败状态，要么移除入口/明确标注“仅保存在本机”，不能继续显示已提交成功。

### P2-03 `storageLocation` 缺少服务端长度限制

**证据**

- 保存校验只检查它是字符串并 `trim`：`cloudfunctions/inventoryApi/validation.js:72-77`。
- 完整表单输入没有 `maxlength`：`miniprogram/components/item-form-sheet/index.wxml:150-157`。
- AI 结果允许到 500 字符：`cloudfunctions/quickEntryApi/ai-parse.js:102`、`date-facts.js:95`。

**影响**

异常客户端可以写入很长文本，放大数据库文档、列表响应、WXML 渲染和订阅模板处理成本。客户端限制不能替代服务端边界。

**建议**

按产品展示确定统一上限（建议 40～100 个码点），服务端强制校验，前端同步 `maxlength`，历史超长数据展示时截断但不要静默破坏原数据。

### P2-04 批量操作页会拉完整个筛选结果，没有数量和内存上限

**证据**

`miniprogram/pages/batch-operation/index.ts:98-132` 持续翻页直到游标为空，并把全部记录放入 `items`；首页和回收站虽限制为 200 项，批量页没有同类上限或虚拟列表。

**影响**

大账户会产生多次串行云调用、较大的 `setData` 负载和数百/数千节点，进入批量页即可卡顿；之后全选还会进行大量分块写调用。

**建议**

MVP 最简单的方案是设置明确上限并提示继续缩小筛选；若确实需要“全量批处理”，改为服务端按查询条件创建批任务，不在客户端加载全部文档。

### P2-05 最近录入档案先截 100 条再去重，可能过早丢失候选

**证据**

主路径只查询最近 `limit` 条，再按名称去重：`cloudfunctions/inventoryApi/index.js:109-117`、`cloudfunctions/inventoryApi/recent.js:116-128`。

**影响**

若最近 100 条大部分同名，接口可能只返回少数档案，即使第 101 条之后还有大量不同名称。当前测试验证了“只查询一次”，没有覆盖高重复率下的产品语义。

**建议**

一次多取 `limit × 2`（仍限制最大 200～300）再去重，或在结果不足时最多补一页；这是比恢复 24 次查询更平衡的方案。

### P2-06 历史/回收站仍使用偏移分页，写入期间可能重复或漏项

**证据**

`listHistory/listTrash` 使用 `skip(offset)`：`cloudfunctions/inventoryApi/index.js:544-599`。`listHistory` 的游标甚至没有查询签名，`listTrash` 虽有签名但仍受偏移漂移影响。

**影响**

翻页期间若有删除、恢复或新条目插入，偏移会移动，出现重复/漏项；深分页成本也会随 offset 增长。当前 UI 的 200 项上限降低了风险，但批量页会继续翻到底。

**建议**

复用库存页的键集分页，按 `completedAt + _id` 做稳定游标，并带查询签名。

### P2-07 高频数量调整走完整保存事务，已有轻量减量接口却未使用

**证据**

- 首页 `±1` 和直接改数都调用 `updateQuantity`：`miniprogram/pages/home/index.ts:450-479`。
- `updateQuantity` 把完整物品重新提交给 `save`：`miniprogram/services/inventory-service.ts:75-80`，服务端会进入事务并读取提醒任务。
- 更轻量的 `decrementItem` 已存在但全仓无调用方：`miniprogram/services/inventory-service.ts:82-88`。
- 数量变化不会改变 expired/expiring/safe 统计，首页却仍把概览标脏：`miniprogram/pages/home/index.ts:478-479`。

**影响**

高频点按产生不必要的完整字段校验、事务、提醒读取和后续概览重算，增加延迟与云调用费用。

**建议**

新增一个带 `version` 的 `setQuantity`/`adjustQuantity` 条件更新，或至少让减量复用现有 `decrement`；成功后只 patch 行数据，不失效概览。

### P2-08 云函数依赖存在上游安全审计告警

**审计结果（2026-09-13）**

- 以 `inventoryApi` 为代表的 `wx-server-sdk@4.0.2` 锁文件：5 个 high、1 个 moderate，来自上游 `@cloudbase/node-sdk → @cloudbase/database/axios/lodash.set/lodash.unset`。
- `quickEntryApi`：在上述基础上增加 `tencentcloud-sdk-nodejs-common → uuid`，合计 5 个 high、3 个 moderate。
- 根工程生产依赖审计为 0。

**判断**

这是上游依赖告警，不等于项目已可被直接利用。当前代码限制了身份字段、数据库字段和多数输入长度，也没有把用户输入直接作为 SDK 请求 URL；但 `npm audit` 建议的所谓修复是把 `wx-server-sdk` 降到 `2.5.3`，不能直接执行，可能破坏当前 AI 与云开发能力。

**建议**

记录并跟踪微信官方 SDK 修复版本；升级时先在独立分支运行单测和云环境回归。短期继续保持字段白名单，避免把用户可控对象直接传入数据库更新或 SDK 配置；为依赖审计建立定期检查，而不是使用 `npm audit fix --force`。

## 5. 性能评估

### 5.1 当前表现较好的设计

- 首页首次列表可顺带返回概览，减少一次云函数 RTT。
- 库存页设置递增请求序号，旧响应不会覆盖新筛选结果。
- 库存列表最多渲染 200 条，图片使用懒加载；封面已降到 512×512。
- 批量库存写限制 5 路并发，提醒派发限制 8 路，回收站清理限制 10 路，能降低数据库冲突与限流峰值。
- 快速录入的 AI 调用有超时、缓存和本地规则降级，主流程不会因模型失败完全不可用。

### 5.2 主要瓶颈与扩展边界

| 区域 | 当前边界 | 风险 | 建议触发条件 |
| --- | --- | --- | --- |
| 首页概览 | 先拉最多 1,000 条投影到函数内聚合，满 1,000 再做 4 次 count | 接近阈值时一次请求可能同时承担扫描与 count | 用真实日志观察 P95；单用户接近 500～1,000 条时改为聚合管道或分桶计数 |
| 名称/位置搜索 | 包含正则 + OR | 难以充分利用普通索引 | 家庭规模可接受；P95 超标或单用户数百条后再评估前缀搜索 |
| 回收站/历史 | `skip` 偏移分页 | 深页成本和并发漂移 | 与稳定游标修复一起完成 |
| 批量页 | 拉全量、无虚拟化 | 网络、内存、节点数线性增长 | 发布前至少增加上限 |
| 数量调整 | 完整 save 事务 | 高频操作放大 RTT 与读写次数 | 可直接优化，不需等待规模增长 |
| 快录云函数 | 同一函数打包 AI、规则、ASR、OCR 适配 | 冷启动包和初始化成本较大 | 先测冷启动 P95；语音/照片长期启用后再决定是否拆函数 |
| 图片 | 直接用 512 原图作为列表图 | 首屏多图仍有流量压力 | 云存储图像处理开通后生成真正缩略图；此前保持懒加载 |

不建议现在引入 Redis、消息队列、全文检索或前端状态库。先修正确性，再依据云函数 `durationMs`、We 分析首屏事件、数据库读次数和真实用户规模决定是否扩展。

## 6. 测试与可观测性缺口

1. **真实 schema 契约缺失。** 导出测试使用旧提醒字段就是直接例证。建议用生产写路径输出作为其他模块测试夹具，避免手写两套结构。
2. **分页边界缺失。** 没有覆盖同 `createdAt`、同 `expiryDate`、跨页并发新增/删除。
3. **缓存跨页失效缺失。** 没有覆盖表单、详情、快录、批量、注销返回首页后的概览。
4. **定时任务故障注入不足。** 需要覆盖 claim 前失败、claim 后失败、发送成功但状态更新失败、僵尸 `sending`。
5. **文件生命周期缺失。** 需要验证共享封面、永久删除、30 天清理、注销和并发生图。
6. **没有覆盖率门槛。** 不必追求 100%，但建议先输出覆盖率报告，对 `inventoryApi`、`dispatchReminders`、`userApi/export` 设置关键分支门槛。
7. **缺少自动化集成记录。** `tests/integration/README.md` 只有说明。建议保留开发/生产环境的最近一次双账号隔离、提醒真机闭环、删除清理与并发版本测试日期和结果。
8. **发布配置未纳入检查。** 当前 `npm run check` 在模板 ID 为 TODO、文档时间冲突时仍全部通过。

云函数日志已有 `requestId/action/resultCode/durationMs`，基础不错；仍建议增加：

- 提醒任务按阶段统计，以及 `scheduled due`、超龄 `sending`、`unknown` 的数量告警。
- AI 解析和生图的每日调用量、缓存命中、额度拒绝、平均费用估算与全局熔断状态。
- 清理任务的失败条数和剩余待清理数量，而不仅是成功删除数。
- 封面总文件数、总字节数和无引用文件抽样检查。

## 8. 推荐修复顺序

### 发布前必须完成

1. 收敛提醒模板、字段、时间和发布状态配置，补自动发布检查及真机闭环。
2. 修复首页概览跨页失效，并同时修复概览卡保留筛选的问题。
3. 修复导出提醒字段，升级导出 schema 并补真实契约测试。
4. 给库存游标增加 `_id` 唯一键，补并列时间戳分页测试。
5. 明确封面文件生命周期、额度与隐私声明；至少先把开关改为显式开启并增加额度保护。
6. 修复派发异常状态落库与僵尸任务对账。
7. 处理“意见反馈”假成功，并给存放位置增加服务端长度限制。

### 发布后第一阶段

1. 将回收站/历史改为稳定游标。
2. 限制批量页加载规模。
3. 优化数量调整写路径，移除无效概览失效。
4. 修正最近档案高重复率截断。
5. 建立依赖告警跟踪和关键模块覆盖率门槛。

### 暂不建议做

- 不建议为了“架构更漂亮”改成跨端框架或引入全局状态库。
- 不建议在没有真实 P95 和用户规模前引入缓存服务、全文检索、消息队列。
- 不建议直接运行 `npm audit fix --force` 降级微信 SDK。
- 不建议一次拆完三个大页面；应在修对应功能时提取明确的纯逻辑或子组件。

## 9. 验收标准

完成上述修复后，至少满足以下条件再重新评估发布：

- `npm run check` 通过，并新增发布配置检查。
- 新增、编辑、用完、删除、恢复、批量、注销后首页概览立即正确。
- 真实 reminder job 经导出后字段完整，schema 版本明确。

- 任意派发阶段失败后，任务最终进入可解释状态，不长期停在 `sending`。
- 体验版真机完成订阅提醒、消息跳转、双账号隔离、弱网和账号注销闭环。
